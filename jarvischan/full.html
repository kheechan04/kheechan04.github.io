마이크 하나, 브라우저 음성 API 셋,
그리고 다섯 번의 재설계

영화 속 JARVIS처럼 말로 묻고 답하는 음성 비서 Jarvischan을 Vercel에 무료로 배포하고, 실제로 써보면서 나온 문제들을 하나씩 잡아나간 기록이다. Claude Code를 페어 삼아 코드를 고치고 바로 재배포해서 다시 테스트하는 방식으로 작업했고, 이 문서엔 "어떻게 고쳤는가"뿐 아니라 "왜 처음 시도가 틀렸는지"까지 남겨뒀다 — 특히 2장(무음 판정)은 같은 문제를 다른 각도로 네 번 다시 풀다가 결국 접근 자체를 바꾼 과정이라, 나중에 비슷한 문제를 만났을 때 제일 먼저 펼쳐볼 장이다. 이후 실기기(아이패드)로 재확인하며 또 한 라운드의 문제를 잡았고, 서버가 닿을 수 없는 "내 컴퓨터를 직접 제어하는" 기능(로컬 에이전트)까지 새로 얹으면서 문서를 이어 썼다.

기능 추가 → 버그 발견·수정

웨이크워드, 그리고 마이크를 두고 벌어진 경합

박수 두 번으로 깨우는 기능은 있었지만 "박수를 못 치거나 기기에서 멀리 떨어져 있을 때"는 무력했다. 브라우저 내장 음성인식을 웨이크워드 감지에 재사용하는 기능을 추가하자마자, 그 인식기와 실제 받아쓰기(Whisper)용 마이크 스트림이 서로 자리를 두고 부딪히는 문제가 나왔다.

계기 "박수를 못 치는 상황"에 대한 사용자 질문 재사용 API 브라우저 SpeechRecognition

1.0설계 — 왜 별도 API 재사용인가

대안으로 "항상 듣고 있다가 음량이 사람 목소리 수준으로 올라오면 자동 시작"하는 방식도 검토했지만, 박수 감지처럼 소리 크기만으로는 오탐이 많을 게 뻔했다. 대신 이미 Whisper 폴백으로 코드베이스에 들어있던 브라우저 SpeechRecognition을 계속 듣는 모드(continuous:true)로 돌리면서 "Jarvis" / "자비스"가 들리는지만 검사하는 쪽을 택했다 — 별도 API 비용 없이, 대화가 진행 중이 아닐 때(idle)만 동작하게 감시 루프를 하나 더 둬서 자기 자신의 응답 음성(TTS)을 웨이크워드로 잘못 알아듣는 것도 막았다.

1.1버그 — 대화가 조용해져도 끝나지 않음

기능은 잘 작동했지만, 실사용 테스트에서 "말이 끝났는데 녹음이 전혀 끝나지 않는다"는 문제가 나왔다. 원인은 타이밍이었다: 웨이크워드를 인식한 즉시 그 SpeechRecognition 세션을 멈추고 곧바로 Whisper용 getUserMedia를 호출했는데, Chrome이 이전 세션의 마이크를 실제로 놓기(release) 전에 새 스트림을 요청하면 MediaRecorder가 "녹음 중" 상태로는 보이지만 실제로는 오디오를 전혀 못 받고 종료 이벤트도 안 나는 상태로 멈춰버렸다.

진단

브라우저 음성 API 두 개(SpeechRecognition, getUserMedia)가 같은 마이크 하드웨어를 두고 빠르게 넘겨받으려 하면, 겉으로는 에러 없이 성공한 것처럼 보이면서 실제로는 죽어있는 상태가 될 수 있다 — 두 API 모두 마이크 해제/획득이 비동기라는 게 문서에는 잘 안 드러난다.

해결: 웨이크워드 인식기의 stop()을 호출한 뒤, 실제로 세션이 끝났다는 신호 (onend)를 받고 나서야 Whisper 녹음을 시작하도록 순서를 바꿨다. onend가 안 오는 예외 상황에 대비해 400ms 타임아웃도 안전장치로 같이 걸었다.

교훈

브라우저 API를 이어붙일 때는 "성공적으로 시작됐다"와 "이전 리소스가 실제로 해제됐다"를 다른 신호로 취급해야 한다. 특히 마이크·카메라처럼 하드웨어를 공유하는 API는 더더욱.

1.2또박또박 말해야만, 그리고 시간이 지날수록 인식이 안 됨

마이크 경합 문제를 고친 뒤에도 실사용 피드백이 이어졌다 — "처음엔 잘 되는데 그 다음부터 인식을 잘 못하는 것 같고, 완전히 또박또박 발음해야만 인식되는 것 같다"는 것. 원인은 두 가지가 겹쳐 있었다.

진단 1 — 사전에 없는 이름

웨이크워드 정규식이 자비스찬/jarvischan 문자열을 정확히 그대로 매칭해야만 통과되도록 짜여 있었다. "자비스찬"은 사전에 없는 만든 이름이라, 구글 음성인식이 조금만 웅얼거려도 비슷한 다른 음절("자비스잔", "자비스 찬" 등)로 잘못 받아적기 쉬운데, 그러면 곧바로 매칭 실패였다. "또박또박 말해야만 인식된다"는 증상과 정확히 들어맞았다.

진단 2 — 연속 인식 세션의 열화

대기 상태에서 계속 듣고 있는 SpeechRecognition 세션(continuous:true)을 하나만 계속 붙잡고 쓰고 있었는데, 크롬의 이 API는 같은 세션을 오래 켜둘수록 인식 정확도가 눈에 띄게 떨어지는 — 공식 문서엔 안 나오는 — 특성이 있었다. "처음엔 잘 되다가 그 다음부터 안 된다"는 증상은 바로 이거였다.

해결은 두 갈래였다. 정규식을 자비스/jarvis 같은, 헷갈리기 어려운 핵심 음절만 매칭하도록 완화하고 maxAlternatives:3으로 1순위 인식 후보뿐 아니라 대안까지 검사하게 했다. 그리고 대기 세션이 15초를 넘기면(실제로 열화가 체감되던 시점보다 훨씬 이르게) 자동으로 새 세션으로 교체하도록 감시 루프를 추가했다.

같은 문제, 다섯 번의 재설계

"말이 끝났다"를 어떻게 아는가

사용자가 말을 마치면 자동으로 녹음을 끝내는 기능(VAD, 음성 활동 감지)이 실사용 중 계속 문제를 일으켰다. 매번 증상은 다르게 나타났지만("영원히 안 끝남" → "10초씩 걸림" → "그래도 안 끝남"), 근본 원인은 하나로 수렴했다 — 마이크 음량(진폭)만으로 "사람이 말하고 있는지"를 판단하는 방식 자체의 한계. 이 장은 그 한계를 인정하고 접근을 바꾸기까지의 전체 과정이다.

재설계 5회 최종 해법 브라우저 SpeechRecognition의 onspeechend 재사용

용어배경 지식 — VAD와 SpeechRecognition이 뭔지

VAD(Voice Activity Detection, 음성 활동 감지)는 오디오에서 "지금 사람이 말하는 구간"과 "무음·잡음 구간"을 구분하는 기술을 통틀어 부르는 말이다. 화상회의 앱이 말하는 사람을 자동으로 하이라이트하는 것, 통화 중 무음 구간을 압축하는 것 등 음성 관련 제품 대부분에 어떤 형태로든 들어가 있다. 구현 난이도 순으로 보면 진폭(음량) 기준(가장 단순, 배경 소음에 취약) → 주파수 대역 기준(목소리 대역만 걸러 듣기) → 머신러닝 기반(실제 음성 패턴을 학습한 모델이 판단, 가장 정확하지만 직접 구현하기보다 기존 것을 가져다 쓰는 게 보통)까지 있다. 이 장에서 겪은 재설계 5번은 정확히 이 세 단계를 순서대로 밟아나간 과정이다.

SpeechRecognition은 window.SpeechRecognition(표준) 또는 window.webkitSpeechRecognition(Chrome)으로 접근하는, 브라우저에 내장된 음성인식 API다. Chrome에서는 음성 검색·"Ok Google" 받아쓰기에 쓰이는 구글의 실제 엔진이 뒤에서 동작하며, 오디오를 구글 클라우드로 스트리밍해 인식한다(완전 로컬 처리가 아니다). 주요 이벤트는 onstart(시작) → onspeechstart(말소리 감지) → onresult(인식 결과) → onspeechend(말소리 끝남, 내장 ML 기반 VAD가 판단) → onend(세션 종료) 순으로 발생한다. 이 프로젝트에서는 이 API를 세 가지 용도로 각각 다르게 쓴다 — 로그인 전/Whisper 실패 시 받아쓰기 폴백(결과 텍스트를 실제로 씀), 웨이크워드 감지(idle 상태에서만 계속 듣다가 특정 단어만 매칭), 그리고 이 장의 최종 해법인 무음 판정 대체(onspeechend 이벤트만 쓰고 인식된 텍스트는 버림 — 순수하게 "언제 멈췄는지"를 알려주는 타이머로만 재사용). 아직 W3C 정식 표준은 아니고(커뮤니티 그룹 드래프트 단계), 그래서 브라우저 지원이 Chrome 계열에 치우쳐 있고 세밀한 설정값(예: 무음 판정 민감도)도 노출돼 있지 않다.

2.0최초 설계 — 녹음 시작 300ms의 스냅샷

최초 구현은 녹음이 시작되고 첫 300ms 동안의 평균 음량을 "조용한 방의 기준(floor)"으로 딱 한 번 재고, 그 이후 음량이 floor + 0.035 밑으로 1.2초 이어지면 대화가 끝났다고 판단하는 방식이었다.

증상 — 조용해져도 안 끝남

조용한 방이 아니면 재현됐다. 녹음 시작 직후의 300ms가 우연히 더 조용했거나, 이후 생활 소음 (에어컨, 도로 소음)이 커지면 그 소음 자체가 계속 floor + 0.08(말하는 중 기준)을 넘어서 영원히 "말하는 중"으로 오분류됐다. 한 번 정한 기준을 끝까지 고정해서 쓰는 게 문제였다.

2.11차 재설계 — 3초마다 기준 재보정

고정 스냅샷 대신, 3초 창(window)마다 그 구간에서 가장 낮았던 음량으로 기준을 다시 앵커링하도록 바꿨다. 사람 말소리는 단어·숨 사이에 짧은 공백이 있어서 창의 최솟값이 여전히 낮게 잡히지만, 꾸준히 일정한 생활 소음은 창 전체가 비슷한 값이라 자연스럽게 새 기준으로 흡수된다는 논리였다. 이 자체는 맞아떨어져서, "조용한 방이 아니면 안 끝남" 문제는 해결됐다.

2.22차 재설계 — 목소리 대역만 보기

그런데 재보정 이후에도 일부 상황에서 여전히 끝나지 않는 경우가 있었다. 원인을 다시 보니, 음량을 analyser의 64개 주파수 빈 전체(초저음 웅웅거림부터 초고음 히스노이즈까지)를 뭉뚱그려 평균 내고 있어서, 목소리와 무관한 소음이 신호 대부분을 차지하고 있었다. 사람 목소리가 실제로 실리는 대역(약 300Hz~3.4kHz)에 해당하는 빈만 골라 평균 내도록 바꿨다 — 표본 주파수를 알아야 정확한 빈 인덱스를 계산할 수 있어서, audioCtx.sampleRate 기반으로 동적으로 범위를 산출했다.

2.33차 재설계 — 좁힌 대역의 부작용, 스무딩

증상 — 이번엔 10초씩 걸림

대역을 좁히자(64개 → 약 8개 빈) 측정값 자체가 훨씬 들쭉날쭉해졌다. "조용함" 1.2초 연속 판정이 잡음 스파이크에 계속 리셋되다가 우연히 깨끗한 구간을 만나야만 통과되는 패턴이 돼서, 체감상 녹음 종료까지 10초 가까이 걸렸다.

VAD 판정에 쓰는 값에만 지수이동평균(EMA, 새 값 가중치 0.45)을 가볍게 걸어서 안정시켰다. 화면 비주얼라이저용 레벨 값은 건드리지 않아서 시각적 생동감은 그대로 유지했다.

2.44차 재설계 — 접근을 바꾸다

스무딩까지 넣었는데도 정적 구간이 여전히 길다는 피드백이 왔다. 여기서 멈추고 다시 생각했다: 진폭 기준 VAD는 아무리 다듬어도 "말이 끝났다"를 소리 크기만으로 판단하는 방식 자체에 천장이 있다. 반면 브라우저의 SpeechRecognition은 실제 받아쓰기 제품에 쓰이는, 훨씬 정교하게 튜닝된 자체 음성종료 감지(onspeechend)를 이미 내장하고 있다.

Whisper 녹음(MediaRecorder)과 별개로, 텍스트는 전혀 쓰지 않고 종료 신호만 받는 보조 인식 세션을 하나 더 띄워서 onspeechend가 뜨면 바로 녹음을 멈추도록 바꿨다. onend만으로는 트리거하지 않는다 — 말을 시작하기도 전에 인식기가 포기하고 끝나버리는 경우까지 "종료"로 오인할 위험이 있어서다. 기존 진폭 VAD와 7초/20초 하드캡은 이 API를 지원 안 하는 브라우저나 이벤트가 안 오는 예외 상황을 위한 백업으로 남겨뒀다.

이 장에서 남은 교훈

증상이 바뀔 때마다 파라미터를 손보는 것도 유효한 디버깅이지만, 몇 번을 다듬어도 근본 한계가 반복해서 드러난다면 파라미터가 아니라 접근 자체를 의심해야 한다. 특히 브라우저가 이미 잘 풀어놓은 문제(음성 종료 감지)를 손으로 재발명하려 했던 게 애초에 무리였다 — 그 API를 "받아쓰기 품질"이 아니라 "타이밍 신호"로만 재사용하면 정확도 걱정 없이 장점만 가져올 수 있었다.

2.5왜 이렇게 정확하고 즉각적인가 — 그리고 그 대가

바꾸고 나서 바로 체감한 차이: 말이 끝나는 순간 거의 "칼같이" 녹음이 멎었다. 이유를 짚어보면 — 이 SpeechRecognition은 손으로 만든 로직이 아니라 Chrome이 음성 검색· "Ok Google" 받아쓰기 같은 실제 제품에 쓰는 구글의 음성인식 엔진 그대로다. 마이크 오디오를 구글 클라우드로 보내서 실제 음성 패턴을 학습한 모델이 "말소리인지 아닌지"를 판단하기 때문에, 진폭 숫자 비교와는 정확도 자체가 다르다. 게다가 이런 제품들은 사용자가 말을 마치고 1~2초씩 멍하니 기다리게 하면 안 되니, 구글이 반응 속도를 의도적으로 매우 짧게(수백 밀리초 단위로 추정) 튜닝해뒀다 — 그래서 즉각적으로 느껴지는 건 버그가 아니라 설계다.

대가 — 정확도와 맞바꾼 것

이 정확도엔 두 가지 대가가 따른다. 첫째, 튜닝 손잡이가 없다 — "1초는 더 기다려줘" 같은 설정을 API가 노출하지 않아서, 반응 속도가 안 맞아도 직접 조절할 방법이 없다. 둘째, 오디오가 구글 서버로 나간다 — 받아쓰기 자체는 여전히 Whisper가 하지만, "언제 멈췄는지"만 물어보는 이 보조 세션도 똑같이 클라우드를 거친다. 정확도를 사는 대신 로컬 처리와 세밀한 제어권을 내준 셈이다. 실사용 중 "말하다 잠깐 멈췄는데 끊겼다"는 사례가 잦아지면, 지금 백업으로 남겨둔 진폭 기준 VAD와 섞어 약간의 여유를 주는 하이브리드로 조정할 계획이다.

2.6모바일에서 재발 — 예상과는 다른 원인

노트북(크롬)에서는 문제가 없었다. 그런데 아이패드로 실사용을 재확인하자 "말이 끝났는데 20초 하드캡까지 전혀 안 끊긴다"는 증상이 다시 나왔다 — 위 2.5에서 예상했던 "가끔 말하다 멈췄는데 끊기는" 것과는 정반대 방향의, 더 심한 재발이었다. ?debug=1로 로그 패널을 띄워 실기기 로그를 직접 받아보며 원인을 하나씩 좁혔고, 예상과 다른 세 가지가 겹쳐 있었다.

원인 1 — iOS엔 애초에 onspeechend가 없음

로그에 speech-end no browser endpointer — VAD only만 찍히고 그 뒤로 조용했다. 2.4에서 1차 신호로 쓰기 시작한 브라우저 자체 종료감지가 iOS Safari에는 아예 없거나 있어도 이벤트가 안 왔다 — 그래서 모든 기기에서 항상 돌아가던 백업, 즉 진폭 기준 VAD로 고스란히 떠넘겨졌다. 그런데 그 백업이 기대했던 "조용한 방 = 거의 0"이라는 전제 자체가 모바일에서는 성립하지 않았다 — getUserMedia({audio:true})가 기본으로 켜는 autoGainControl이 배경 소음까지 끌어올려서, 원래도 약점이었던 진폭 기준 판정이 한 번 더 흔들린 것.

해결 1

Whisper 녹음 스트림도 autoGainControl:false로 열어 가공 안 된 원본 음량을 읽게 했다. iOS에서는 어차피 못 쓰는 보조 인식 세션 생성 자체를 건너뛰어, 마이크 하드웨어를 두고 벌어질 수 있는 불필요한 경합 위험도 같이 없앴다.

원인 2 — "조용함" 기준의 상한이 진짜 소음보다 낮았음

AGC를 껐는데도 20초 하드캡까지 그대로였다. 로그를 다시 보니 floor(조용함 기준)가 정확히 0.100에 고정된 채 끝까지 움직이지 않고 있었다. 코드에 Math.min(0.1, …)로 상한이 박혀 있었던 것 — AGC가 켜져 있던 시절엔 조용한 방의 진짜 음량이 늘 0.1보다 훨씬 낮았기 때문에 안전한 상한이었지만, AGC를 끄고 나니 그 기기·환경의 진짜 주변 소음이 0.17~0.6 사이로 0.1보다 높았다. floor가 진짜 값을 따라갈 수조차 없는 상태였다.

해결 2

상한을 0.7로 올렸다 — 목표값이 아니라 폭주 방지용 안전장치일 뿐이라, 실측된 0.17~0.6 범위에 충분한 여유를 두고 잡았다.

원인 3 — 기준을 따라잡는 속도 자체가 너무 느림

상한을 풀고 나니 이번엔 stop → vad-quiet가 실제로 찍히긴 하는데, 말이 끝나고 17초 뒤에야 찍혔다. floor가 3초 창마다 "이전 값 절반 + 이번 구간 최솟값 절반"으로만 재보정하고 있어서, 목표 주변 소음값에 수렴하기까지 5~6번의 창(15초 이상)이 걸리고 있었다.

해결 3

창을 1.2초로 줄이고, 절반만 섞는 대신 그 구간의 최솟값으로 바로 스냅하도록 바꿨다. "조용함" 확정 대기시간도 1.2초 → 0.8초로 같이 줄여서, 체감 지연을 한 번 더 줄였다.

이 장에서 남은 교훈 (2)

2.4/2.5에서 예상했던 대가("가끔 너무 빨리 끊길 수 있다")와 실제로 터진 문제("아예 안 끝난다")는 정반대 방향이었다 — 미리 세운 가설이 있어도, 실기기·실사용 로그가 나오면 가설을 버릴 준비를 해야 한다. 그리고 같은 파라미터(AGC, 상한값, 재보정 속도)라도 "데스크톱에서 안전했던 값"이 "모바일에서도 안전하다"는 보장은 전혀 없다는 것 — 특히 브라우저의 오디오 전처리(AGC 등)가 플랫폼마다 공격적인 정도가 크게 다르다는 게 셋 다를 관통하는 근본 원인이었다.

Chrome 버그 우회

답변이 길면 음성이 중간에 끊기는 문제

답변이 조금만 길어지면 특정 지점에서 소리가 뚝 끊겼다. Chrome의 오래된 버그였고, 첫 수정은 절반만 맞았다 — 한국어라는 변수를 놓쳤다.

3.0원인 — Chrome의 긴 발화 컷오프 버그

Chrome은 SpeechSynthesisUtterance 하나가 대략 15초 이상 이어지면, onend· onerror 어느 쪽도 발생시키지 않은 채 그냥 재생을 멈춰버리는 오래된 버그가 있다. 답변 전체를 통짜 발화 하나로 넘기고 있었던 게 문제였다.

3.11차 수정 — 문장 단위 큐, 그리고 절반만 맞았던 이유

답변을 문장 단위(최대 180자)로 잘라 순서대로 speak()를 호출하는 큐 방식으로 바꿨다. 영어 기준으로는 충분히 안전한 길이였다.

재발 — 한국어에서만

한국어 답변에서 여전히 끊겼다. 한국어는 글자당 발음 시간이 영어보다 길어서, 같은 180자라도 실제 재생 시간이 영어보다 훨씬 길어 Chrome의 컷오프 한계를 다시 넘었다. 청크 크기를 문자 수로만 관리하면 언어별 발화 속도 차이를 놓친다는 걸 뒤늦게 알았다.

청크 크기를 80자로 줄이고, 마침표 없이 이어지는 긴 문장(쉼표만 있는 나열형 답변 등)은 단어 경계 기준으로 강제 분할하도록 추가했다.

3.22차 수정 — 소리는 다 나왔는데 화면이 멈춤

청크 분할 이후에도 가끔 "소리는 끝까지 다 들렸는데 화면 상태가 계속 RESPONDING에 멈춰있다"는 증상이 남았다. 마지막 청크의 onend가 간헐적으로 아예 발생하지 않는, Chrome 음성 이벤트 자체의 신뢰성 문제였다. 청크마다 글자 수 기반으로 예상 재생 시간을 추정해 안전장치 타이머를 같이 걸어서, onend가 안 와도 강제로 다음 단계로 넘어가게 했다.

교훈

브라우저가 쏘는 완료 이벤트(onend)를 유일한 진행 신호로 믿지 않는다. 특히 음성 관련 Web API는 구현 신뢰성이 낮은 편이라, 이벤트 기반 로직에는 항상 타임아웃 기반 안전장치를 같이 두는 게 안전하다.

배포 파이프라인이 막혔던 이야기

CLI로 여러 번 잘 배포되던 프로젝트가, GitHub 연동을 시작한 직후부터 몇 시간째 배포가 UNKNOWN 상태로 멈추기 시작했다. 진짜 원인은 예상 밖의 곳에 있었다.

증상 모든 배포가 상태 UNKNOWN, 빌드 로그 없음 제거해나간 원인 후보 4개

4.0증상 — 배포마다 조용히 멈춤

GitHub 저장소를 새로 만들고 연동한 직후부터, CLI로 재배포를 시도하든 git push로 트리거하든 배포가 전부 UNKNOWN 상태에서 멈췄다. 대시보드에는 "Fix Git Configuration" 버튼만 떴고, 빌드 로그는 아예 비어 있었다.

4.1후보를 하나씩 제거

  • Vercel 계정에 GitHub 로그인 연결 안 됨. 연결했지만 안 풀림.
  • GitHub에 Vercel 앱이 설치 안 돼 있음. All repositories 권한으로 설치했지만 안 풀림.
  • Root Directory 미설정. 저장소 루트에는 빌드 가이드 md와 실제 앱 폴더 (jarvis-vercel/)가 같이 있는데, Vercel은 기본값(.)으로 루트를 빌드하려 하고 있었다. jarvis-vercel로 지정했지만 여전히 안 풀림.

세 가지를 다 해결했는데도 새 배포가 또 UNKNOWN으로 멈추자, 더 이상 추측성 설정 변경을 반복하지 않고 사용자에게 Vercel 대시보드에서 정확한 메시지를 직접 확인해달라고 요청했다.

4.2진짜 원인 — 로컬 git 설정

Vercel이 보낸 이메일에서 발견

Vercel이 실제로 보낸 알림 이메일: "khchan04@naver.com attempted to deploy a commit … but they're not a member of the team." 로컬 git 전역 설정에 예전부터 박혀있던 커밋 작성자 이메일이, Vercel 팀의 어떤 멤버 계정과도 매칭되지 않아 배포를 조용히 계속 보류시키고 있었다 — GitHub 로그인·앱 권한·Root Directory와는 전혀 무관한, 순수 로컬 git 메타데이터 문제였다.

GitHub 계정에 연결된 공식 noreply 이메일(gh api user로 계정 id 확인 후 {id}+{username}@users.noreply.github.com 형식으로 구성)로 이 저장소에 한해 git config user.email을 맞췄다. 새 커밋을 푸시하자 29초 만에 정상 배포됐다.

교훈

에러 메시지가 모호하거나(그냥 UNKNOWN, 빌드 로그 없음) UI에 뜨는 버튼 문구가 실제 원인을 정확히 짚어주지 않을 때는, 겉보기에 무관해 보이는 설정(이번엔 로컬 git 전역 설정)까지 의심 범위에 넣어야 한다. 그리고 계속 같은 실패가 반복되면 추측으로 설정을 더 바꾸기보다, 시스템이 실제로 보내는 원본 메시지(이번엔 이메일)를 직접 찾아보는 쪽이 빨랐다.

신규 기능 → 세 번의 실기기 버그 수정

서버가 못 닿는 곳 — 로컬 에이전트로 노트북 제어

"가벼운 대화 말고는 할 수 있는 게 없어서 비서라 하기 민망하다"는 게 출발점이었다. 앱을 열고 닫고, 화면을 잠그고, 스크린샷을 찍는 — 사용자의 실제 컴퓨터에 손을 대는 기능을 새로 설계하고 만든 기록이다.

계기 "노트북/폰/패드 앱에 접근하고 실행하는 기능을 넣고 싶다" 새 구성요소 local-agent/ (Node WebSocket 서버) 지원 명령 8개

5.0설계 — 왜 서버가 아니라 별도 프로그램인가

기존 도구(날씨·환율 등)는 전부 Vercel 서버(api/chat.js)에서 직접 실행된다. 그런데 서버는 인터넷에 열려있지 않은 사용자의 개인 컴퓨터에는 원천적으로 닿을 방법이 없는, 상태 없는 클라우드 함수다. 그래서 "앱을 열어줘"는 서버가 아니라 사용자의 컴퓨터에서 직접 실행되는 별도 프로그램이 처리해야 한다는 결론에 먼저 도달했다.

노트북에서 실행하는 작은 Node WebSocket 서버(local-agent/)를 만들고, 웹페이지가 브라우저에서 ws://localhost:8765로 직접 붙게 했다. 크롬은 https 페이지에서 localhost로의 연결은 mixed-content 정책 예외로 허용해서, 별도 인증서 없이 바로 됐다. LLM이 open_app 같은 도구를 호출하면 서버는 실행하지 않고 {"{"}type:"device"{"}"} 형태의 액션만 만들어 브라우저로 돌려주고(이미 있던 타이머 도구와 같은 패턴), 브라우저가 그 액션을 에이전트로 중계해서 실제로 실행한다.

권한 범위는 처음부터 화이트리스트로 제한했다 — 앱 실행도 등록된 것만, 임의 셸 명령 실행·파일 삭제·컴퓨터 종료/재시작·포커스된 창에 텍스트 자동 입력은 의도적으로 넣지 않았다. 음성 인식이 잘못 들었을 때 되돌리기 어렵거나 위험한 동작이라, 나중에 별도 확인 절차부터 설계하면서 넣는 게 맞다고 판단했다.

5.1스크린샷이 화면 일부만 담김

스크린샷 기능을 테스트해보니 화면 전체가 아니라 일부만 잘려서 저장됐다. PowerShell로 직접 두 값을 비교해서 원인을 확인했다.

진단 — DPI 비인식

PowerShell 프로세스는 기본적으로 DPI-aware가 아니어서, 배율 100%를 넘는 디스플레이(요즘 노트북 대부분)에서 .NET이 실제 해상도 대신 축소된 "논리 해상도"를 기준으로 캡처하고 있었다. 실측: 실제 화면은 2560×1600인데 DPI 인식 전엔 1707×1067로 잡혔다(정확히 150% 배율만큼 축소된 값).

캡처 스크립트 맨 앞에서 user32.dll의 SetProcessDPIAware()를 호출해 프로세스를 DPI-aware로 전환했다. 여러 모니터를 쓰는 경우까지 대비해 PrimaryScreen.Bounds 대신 전체 가상 화면을 뜻하는 SystemInformation.VirtualScreen을 쓰도록 같이 바꿨다.

5.2앱을 강제로 끄면 저장 안 한 내용이 그냥 날아감

기능을 다 붙이고 나서 스스로 리뷰하며 짚은 문제다 — close_app이 처음부터 taskkill /F를 무조건 쓰고 있었다. 이건 앱에게 "닫아도 되냐"고 묻지 않고 그냥 죽이는 강제종료라서, 메모장이나 VS Code에 저장 안 한 내용이 있어도 저장 여부를 물어보는 창조차 뜨지 못하고 그대로 사라진다.

이건 실제 사고로 이어질 수 있는 위험

음성 비서 특성상 "메모장 닫아줘"라는 흔한 명령 한마디로 작업 내용이 통째로 날아갈 수 있는 구조였다. 버그 리포트를 받은 게 아니라, 기능을 검증하며 스스로 짚어서 배포 전에 고쳤다.

기본 동작을 /F 없는 정상 종료 요청(WM_CLOSE)으로 바꿨다 — 이러면 앱이 자기 방식대로 저장 여부를 물어볼 수 있다. 그리고 실제로 프로세스가 사라졌는지 확인한 뒤에만 성공으로 보고하고, 안 사라졌으면 "저장 프롬프트가 떠 있을 수 있다"고 알린다. 강제종료는 force:true를 명시적으로 받을 때만 — 그리고 그 값은 사용자가 "강제로 꺼줘"라고 확실히 말했을 때만 LLM이 넘기도록 도구 설명에 못박았다.

5.3연결 버튼이 "connecting"에 멈춤

기능 테스트 중간에 에이전트를 여러 번 재시작하면서(재시작할 때마다 새 페어링 토큰이 생성됨) 브라우저에 저장된 옛 토큰이 못 쓰게 되는 상황이 자연스럽게 반복됐는데, 그때마다 "Local agent" 버튼이 connecting…에 멈춰서 두세 번 눌러야 겨우 토큰 재입력 창이 떴다.

진단

인증 실패 시 저장된 토큰만 지우고 "켜짐" 상태(laOn)는 그대로 남겨두고 있었다. 그러니 버튼은 계속 "connecting…"만 보여주고, 재입력 창을 다시 띄우려면 먼저 꺼짐으로 되돌리는 클릭이 한 번 더 필요했다.

인증 실패를 "켜짐 상태가 유지된 반쯤 실패"가 아니라 완전한 "꺼짐"으로 취급하도록 바꿨다 — 소켓을 닫고 laOn도 같이 꺼서, 바로 다음 클릭 한 번이면 토큰 재입력 창이 뜬다.

5.4마무리 — 자동 재연결과 자동 시작

기능 검증이 끝난 뒤, 스스로 돌아보며 세 가지를 더 다졌다. 손 안 대고 쓰는 게 이 프로젝트 전체의 컨셉인데, 로컬 에이전트만 매번 사람이 개입해야 하는 지점으로 남아 있었기 때문이다.

  • 연결 끊김 자동 복구 — 에이전트 재시작·노트북 절전 같은 예기치 않은 연결 끊김을 그냥 두지 않고 5초 뒤 자동 재시도하도록 함
  • 페이지 열 때 자동 접속 — 저장된 토큰이 있으면 버튼을 누르지 않아도 페이지가 열리는 즉시 자동으로 붙게 함
  • 윈도우 로그인 시 자동 실행 — 시작프로그램 폴더에 바로가기를 추가하는 설치 스크립트를 만들어, 노트북을 켜는 것만으로 에이전트까지 같이 뜨게 함(실제로 설치하고 로그인 시나리오처럼 바로가기로 실행해 정상 동작을 확인)

세 가지를 합치면: 한 번만 페어링해두면 그 이후로는 노트북을 켜고 자비스찬 페이지를 여는 것만으로 완전히 자동으로 연결된다.

이 장에서 남은 교훈

"기능이 동작한다"와 "안전하게 동작한다"는 다른 기준이다 — close_app의 강제종료 문제는 버그 리포트가 아니라 기능을 다 만들고 나서 스스로 검토하다가 발견했는데, 음성 비서처럼 사용자 의도를 매번 정확히 파악하기 어려운 인터페이스일수록 "잘못 들었을 때 얼마나 되돌리기 어려운가"를 기능 하나하나마다 따로 판단해야 한다는 걸 다시 확인했다.

마무리

소회

순위나 점수로 남는 프로젝트는 아니지만, 이 문서에 적어둔 과정 자체는 실전에서 부딪히는 문제의 전형이라고 생각한다. 특히 2장(VAD)은 "고친 줄 알았는데 다른 증상으로 재발"을 세 번 겪고 나서야 접근 자체를 바꾼 경우라, 파라미터 튜닝의 한계를 인정하고 아키텍처를 바꾸는 판단을 언제 내려야 하는지 실감할 수 있었다.

작업 방식도 이전 프로젝트와 달랐다. Claude Code와 실시간으로 "이 증상이 나온다 → 코드에서 원인을 짚는다 → 고친다 → 재배포한다 → 실제로 확인해본다"를 반복하면서, 코드를 직접 짜기보다 증상을 정확히 설명하고, 나온 진단이 맞는지 검증하고, 다음 우선순위를 정하는 쪽에 더 집중했다. 브라우저 오디오·음성 API들(getUserMedia, SpeechRecognition, SpeechSynthesis)이 문서상 스펙보다 훨씬 지저분하게 동작한다는 것, 그리고 배포 파이프라인처럼 "코드와 무관해 보이는" 인프라 문제도 결국 근본 원인을 끝까지 파고들면 항상 명확한 답이 있다는 것 — 여기까지가 첫 번째 라운드에서 가장 크게 남은 것들이다.

실기기(아이패드)로 재확인한 두 번째 라운드는 조금 다른 교훈을 남겼다. 데스크톱에서 안전하다고 확인한 값(AGC 여부, floor 상한, 재보정 속도)이 모바일에서는 하나도 안전하지 않았다 — 같은 코드라도 플랫폼이 바뀌면 처음부터 다시 실측해야 한다는 걸 몸으로 확인한 셈이다. 그리고 로컬 에이전트는 "서버가 못 닿는 곳"이라는 명확한 아키텍처 한계에서 출발해 화이트리스트·페어링 토큰·Origin 검사로 처음부터 범위를 좁혀 설계했는데, 그럼에도 close_app의 강제종료 문제(5.2)는 버그 리포트가 아니라 스스로 검토하다가 뒤늦게 찾았다 — 기능이 "된다"와 "안전하게 된다" 사이의 간극은 항상 따로 확인해야 한다는 걸 다시 배웠다.
