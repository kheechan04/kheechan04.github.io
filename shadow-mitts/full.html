웹캠 하나로 미트를 친다
— 녹화 데이터로 원인을 찾아가며 만든 복싱 게임

트레이너가 대 주는 미트에 "1-2-3" 같은 실제 복싱 번호 콤보를 쳐서 맞히는 브라우저 게임 Shadow Mitts를 만들고, 매일 직접 몸으로 플레이하며 나온 불편을 하나씩 잡은 기록이다. 키보드나 센서 없이 웹캠 영상의 포즈 인식만으로 어느 손으로·어떤 펀치를·언제 쳤는지 판정한다. 설계는 Claude와, 구현은 Claude Code와 함께 했고, 이 문서엔 "어떻게 고쳤는가"보다 "어떻게 원인을 확인했는가"를 더 많이 남겼다 — 특히 3장(녹화 vs 게임)과 4장(잔상)은 짐작으로 고쳤다가 더 나빠진 뒤, 측정 도구를 먼저 만들고 나서야 풀린 문제들이다.

산출물 DESIGN.md 첫 모드 미트 타이밍

1.0내가 정한 것, 제안받은 것

방향은 내가 정했다 — 카메라 인식 방식, 첫 모드는 대전이 아니라 미트 타이밍, 매력 포인트는 타격감과 기록, "창의적인 건 다 고려하되 뻔한 건(리듬 싱크·보스전) 뒤로". 가장 큰 결정은 "지금 대화창에서 만드는 것보다 Claude Code로 옮기는 게 낫지 않냐"는 제안이었다 — 그 세션엔 카메라가 없고 패키지 설치도 막혀 있어서, 설계서만 정리해 넘기고 구현은 몸으로 튜닝할 수 있는 로컬로 옮겼다. 번호 콤보·가드 채점·적응형 출제 같은 차별점과 "타이밍+손+종류로 판정" 같은 방식은 Claude가 제안했다.

1.1포즈 모델 — MediaPipe vs YOLO

처음엔 "OpenCV나 YOLO 같은 것"을 생각했다. 설계 단계에서 MediaPipe Pose와 YOLO-pose를 웹 실행 가능성과 구현 편의성 중심으로 검토해 MediaPipe를 골랐다. 두 모델을 나란히 벤치마크하지는 않았고, 판단 근거와 공식 자료는 저장소의 MODEL-CHOICE.md에 정리했다.

몸을 숫자로 — 펀치 인식

웹캠 한 대는 앞뒤 깊이를 거의 못 본다. 카메라 쪽으로 뻗는 잽은 화면상 거의 안 움직인다. 그래서 직접 동작을 녹화(관절 좌표 JSON — 영상은 저장하지 않음)해 넘기고, 그 데이터를 재생해 규칙을 만들었다.

녹화 19개 · 175펀치 (사우스포 1인) 결과 손 94% · 번호 91% · 오검출 0

2.0좌표축부터 확인 — 깊이는 쓰지 않는다

가만히 가드 자세·잽 10회 등을 녹화해서 x/y/z 축의 방향과 좌우 라벨을 확정했다. 그 과정에서 카메라 쪽으로 잽을 뻗으면 깊이 값(z)이 오히려 뒤로 가고 3D 팔꿈치 각도도 75°→100° 정도만 변한다는 걸 발견해 깊이를 아예 쓰지 않기로 했다. 또 비스듬한 가드 자세에서 두 어깨 좌표가 뒤바뀌며 떨려서, 한쪽 어깨 대신 양 어깨 중점과 몸통 길이를 기준으로 모든 값을 쟀다.

2.1오검출 잡기 — 몸통 회전, 작은 어퍼컷

팔마다 "대기 → 뻗는 중 → 복귀" 상태를 두고, 가드에서 빠르게 멀어졌다가 돌아오면 펀치로 본다. "몸통만 돌렸는데 잽으로 잡힌다"는 문제는 녹화에서 양손이 같이·옆으로·느리게 움직이는 패턴(공통 움직임 0.51~0.92)을 찾아 걸렀다 — 가드만 한 구간·몸통 회전만 한 구간의 오검출 0. 반대로 "어퍼컷을 작게 치면 못 잡는다"는 피드백은, 그 몸통 회전 필터가 작은 어퍼컷까지 버리고 있던 것이 원인이었다. 손이 먼저 살짝 내려가는 "딥"을 추적해 그 바닥점부터 다시 재도록 바꿔 작은 어퍼컷 3/10·2/10 → 8/10·8/10.

2.2높이가 아니라 팔 자세로

처음엔 주먹이 멈춘 높이로 종류를 나눴는데, 직접 해 보니 "얼굴 높이로 치면 잽, 턱 아래면 훅, 머리 위면 어퍼컷"처럼 높이를 맞춰 쳐야만 인식됐다. 실제 복싱은 그렇지 않다. 팔뚝 각도(훅은 팔뚝이 눕는다: −12°~13° vs 나머지 51° 이상), 팔꿈치 높이, 딥 여부로 판단하는 모델로 바꿨다. 판정도 한 순간에 맞히는 리듬게임식은 "너무 빡세다"는 체감 때문에 미트가 도착해 잠깐 머무는 동안 치면 인정하는 "미트 대 주기" 방식으로 바꿨다.

검증 방법

인식 로직은 DOM 없는 순수 TypeScript라, 녹화 JSON을 재생해 채점하는 npm run eval과 녹화·합성 데이터 단위 테스트로 카메라 없이 확인한다. 녹화 성능은 테스트의 최저 기준(floor)으로 고정해 규칙을 고치다 성능이 떨어지면 테스트가 실패한다.

같은 증상, 세 가지 원인

"녹화에선 잘 잡히는데 게임에선 못 잡아"

훅·어퍼컷·연타를 게임에서만 놓친다는 피드백이 몇 번이나 반복됐다. 연습 녹화로 채점하면 멀쩡했다. 원인은 하나가 아니라 세 개였고, 셋 다 "게임 중 데이터"를 직접 보기 전까지는 보이지 않았다.

도구 "이번 판 기록 저장" 게임 기록 4판 · 116펀치

3.0원인 1 — 웹캠이 15fps로 떨어져 있었다

녹화 파일의 프레임 간격을 늘어놓아 보니 16.7ms(60fps) → 33ms(30fps) → 67ms(15fps)로 점점 벌어져 있었다. 컴퓨터가 느려서가 아니라 어두운 방에서 웹캠이 스스로 초당 장수를 줄인 것이다. 60fps 녹화를 15fps로 솎아 재생하자 게임에서처럼 펀치의 약 40%를 놓쳤다 — 재현 성공. 프레임이 드물면 최고 속도가 낮게 재지므로, 최근 프레임 간격에 따라 속도 기준을 30fps~15fps 사이에서 자동으로 낮추고(15fps에서 0.75배), 뻗는 시간 허용치도 늘렸다. 솎은 녹화 100 → 154/175, 오검출은 여전히 0.

3.1원인 2 — 고친 설정이 게임에 적용된 적이 없었다

그래도 "쳤는데 안 맞는다"가 남아서, 게임 중 관절 좌표·미트 일정·판정·프레임 간격을 통째로 저장하는 게임 기록 기능을 만들었다. 기록을 재생하니 제때 친 훅이 지금 코드에선 맞는데 실제 게임에선 MISS였다. 예전 설정값(뻗는 시간 350ms)으로 재생하자 실제 판정과 34/34 일치. 슬라이더를 한 번이라도 움직이면 모든 값이 브라우저에 통째로 저장되는 구조라, 나중에 기본값을 고쳐도 그 브라우저엔 옛 값이 계속 쓰이고 있었다. 이후 설정은 "바꾼 값만" 저장하고, 게임 기록에 당시 설정을 함께 남기도록 했다.

3.2원인 3 — 게임에선 다르게 친다

게임 기록의 펀치를 "그 순간 떠 있던 미트 번호"를 정답으로 삼아 보니, 크게 친 훅과 스트레이트가 어퍼컷으로 잡히고 있었다. 게임에선 치기 전에 손이 살짝 내려가는 "딥"이 생기는데, 딥은 어퍼컷의 특징이었다. 데이터에서 팔꿈치 높이가 둘을 갈랐다 — 딥이 있을 때 훅·스트레이트는 대부분 팔꿈치가 높고(−0.11 이상) 어퍼컷은 대부분 낮았다(−0.23 이하, 예외 2개). "딥이 있어도 팔꿈치가 높으면 어퍼컷이 아니다"로 바꿔 게임 펀치 19 → 27/31(연습 녹화는 163 → 162/168). 잽 미트가 앞손 쪽에 있어서 잽이 위·바깥으로 가던 것도 "주로 위로 뻗으면 바깥 허용"으로 풀었다.

멈출 때를 아는 것

게임 기록이 4판(116펀치)이 된 뒤, 특징값 조합을 바꿔 가며 다시 학습하고 판 하나씩 빼고 검증했지만 지금 규칙(게임 68/81)을 넘는 모델이 없었다. 전체 86%, 훅은 34개 중 32개. 여기서 더 맞추면 판마다 우연에 맞춘 규칙이 되므로 멈췄다 — "데이터가 이 이상은 말해 주지 않는다"는 것도 결과로 남겼다.

짐작 3번 실패 → 측정

끊김과 잔상

"빠른 콤보에서 잔상이 남아 뭐가 진짜인지 헷갈린다", "뭔가 계속 끊긴다" — 가장 오래 걸린 문제였다. 처음 세 번은 원인을 짐작해 고쳤고, 매번 조금 나아지거나 다른 모습으로 더 나빠졌다.

도구 가상 시간 프레임 추적 결과 화면 27 → 60fps

4.0짐작으로 고친 세 번

  1. 다음 차례 미트를 반투명하게 → "더 이상해졌다". 반투명한 미트 자체가 잔상처럼 보였다.
  2. 다음 미트를 멀리 대기시켰다가 앞 미트가 판정되면 출발 → 한 번 늦게 치면 뒤 미트가 줄줄이 밀리고, 멈췄다 튀어 나가는 움직임이 "끊김"으로 보였다.
  3. 같은 번호 미트는 앞 미트가 사라진 뒤 등장 → "친 게 또 뜬다". 새 미트가 같은 길 중간에서 불쑥 나타났다.

4.1프레임마다 위치를 기록하는 검사를 만들다

카메라 없이 게임을 가상 시간으로 한 프레임씩 진행시키며 모든 미트의 화면 위치·크기를 기록하고, "갑자기 나타남·순간 이동·크기 급변"을 자동으로 표시하는 검사를 만들었다. 첫 실행에서 바로 걸렸다 — 맞힌 미트가 사라진 다음 프레임에 다시 생겨나고 있었다. 판정 후 지운 3D 모델을, 목록에 남아 있던 그 미트를 본 렌더 루프가 "모델이 없으니 새로 만들자"며 되살린 것이다. 처음부터 있던 버그라, 앞선 세 번의 수정이 제대로 먹히지 않은 이유이기도 했다.

같은 검사로 찾은 것들

타격 순간 화면 전체를 멈추는 "히트 스톱"이 다른 미트까지 멈췄다가 건너뛰게 만들고, 큰 줌 효과와 무작위 흔들림이 옆 미트를 한 프레임에 20~44px씩 튀게 했다. 멈춤을 없애고, 흔들림은 부드럽게 감쇠하는 진동(한 프레임 6~18px)으로, 미트는 멈춤 없이 시계대로만 움직이게 했다. 타격감은 친 글러브만 미트에 박히는 연출·카메라 반동·집중선으로 대신했다.

4.2끊김의 진짜 원인 — 메인 스레드를 차지한 추론

게임 기록에 프레임 간격을 함께 남겼더니, 포즈 추론 한 번에 약 37ms × 초당 22회 — 메인 스레드 시간의 약 80%를 추론이 쓰고 있었다. 화면은 그 틈에만 그려져 간격 중앙값 37ms, 최대 226ms. 추론을 Web Worker로 옮기고, 추론이 끝나면 새 카메라 프레임을 기다리지 않고 최신 프레임으로 바로 다음 추론을 하도록 했다. 같은 이미지로 메인 스레드와 Worker의 관절 좌표 차이가 0인 것을 확인한 뒤 적용 — 화면 27 → 60fps.

그런데 다음 게임 기록에선 인식이 초당 15회로 줄어 있었다. 화면을 60fps로 그리니 GPU를 3D 렌더링과 나눠 쓰게 된 것. 같은 조건에서 GPU/CPU 두 판을 비교해 CPU 추론을 기본으로 바꿨다(15 → 20회/초, PERFECT 12 → 20). "두 번째 판이 더 잘 맞는 것 같다"는 내 체감과 숫자가 일치했다.

교훈

시각적인 문제는 스크린샷 몇 장으로는 원인이 안 보인다. "무엇이 이상한지"를 숫자로 기록하는 도구를 먼저 만들면, 짐작으로 세 번 고친 것보다 한 번의 측정이 더 많은 걸 알려 준다.

아이디어 → 검토 → 시제품 → 적용

리액션 얼굴과 개인정보

"내 얼굴이 내 실력을 실시간으로 평가하는 복싱 게임" — 내가 낸 아이디어다. 게임 시작 전 얼굴을 찍으면 PERFECT엔 웃는 얼굴, MISS엔 시무룩한 얼굴이 뜨게. 처음 구상은 AI로 표정 이미지를 생성하는 것이었다.

방식 얼굴 좌표 478개 + 메시 변형 전송 0건

5.0생성형 AI를 쓰지 않은 이유

이 게임은 서버 없는 정적 사이트라, 외부 AI로 생성하려면 API 키를 숨길 서버·비용 관리가 새로 필요하고 얼굴 사진이 외부로 나간다. "사진 한 장 → 같은 사람의 다른 표정"은 남의 사진으로 악용될 수도 있다. 그래서 MediaPipe 얼굴 좌표로 사진을 늘리고 당기는 방식을 골랐다. 표정별로 사진을 다 찍는 방식은 내가 "루즈해진다"고 판단해, 한 장만 찍고 변형하기로 했다. 입을 벌린 모습처럼 변형으로 못 만드는 건 치아·입안을 만화 효과로 그려 넣었다. 시제품 페이지를 먼저 만들어 직접 확인한 뒤 게임에 붙였다.

5.1규정 검토와 "안내 문구 = 구현" 검증

  • 개인정보보호법 시행령상 민감정보(생체인식 특징정보)는 특정 개인을 알아볼 목적으로 만든 정보다 — 이 기능은 누구인지 알아보지 않는다. 개인정보보호위원회 생체정보 안내서는 "개인의 특징을 알아보기 위한" 처리까지 넓게 보므로 표정 분석 기능(blendshapes)은 아예 껐다.
  • 얼굴 모델 카드: Apache 2.0, 주 용도 AR 엔터테인먼트, "좌표는 얼굴 인식·신원 확인을 제공하지 않는다".
  • 업로드 없이 실시간 웹캠 촬영만, 찍자마자 원본 프레임 폐기, 메모리에만 보관.
  • 헤드리스 브라우저로 촬영부터 게임·결과까지 모든 네트워크 요청을 기록 — 외부 요청은 글꼴·엔진·모델을 받는 GET뿐, 무언가를 보내는 요청 0건. 그래서 "🔒 사진은 이 기기 밖으로 안 나가요"라고 쓸 수 있었다.
내린 판단 — 필수로 만들지 않음

"사진을 안 찍고 시작하는 사람이 많을 것 같다"는 문제를, 사진 없이는 게임을 못 하게 막는 대신 시작 버튼을 누를 때 한 번 강하게 권하는 방식으로 풀었다. 얼굴 처리를 원하지 않는 사람도 게임은 할 수 있어야 하고, 강제된 동의는 동의가 아니기 때문이다.

테스트엔 실존 인물 사진 대신 AI로 만든 가상 인물 얼굴을 썼다. 검토 문서: FACE-PRIVACY.md (법률 자문 아님).

배포 shadow-mitts.vercel.app 테스트 83개

6.0약점 적응형 출제 · 기록 · 결과 카드

펀치별 정확도의 이동평균을 두고 약한 펀치의 출제 가중치를 최대 3배까지 올린다. 자동 플레이로 5번만 계속 놓치게 하자 다음 판에 5번 비율이 18% → 35%. 점수·펀치별 명중만 브라우저에 저장하고(영상·얼굴 없음), 저장이 막힌 환경에서도 게임은 돌아간다. 결과 카드는 공유용 1080×1350 PNG로, 칼로리 같은 근거 없는 추정치는 넣지 않았다.

6.1처음 방문 체크리스트 — 그리고 페이지를 통째로 멈춘 버그

카메라 켜짐·상체가 다 보임·인식 초당 20회 이상을 실시간으로 ✓ 표시한다. 만들고 바로 헤드리스로 돌렸더니 페이지 전체가 멈췄다 — 체크리스트가 게임 초기화 도중 초당 인식 횟수를 읽어, 아직 선언이 끝나지 않은 변수에 접근(TDZ)한 것. 브라우저에서 직접 해 보기 전에 잡았다.

6.2Vercel과 PWA

"localhost 말고 앱처럼" 쓰고 싶어 배포 방식을 고민했다. 사람들이 써 보는 수는 호스팅 선택과 거의 무관하다는 걸 인정한 위에서, 브랜치별 미리보기와 나중에 서버 기능을 붙일 여지 때문에 Vercel을 골랐다(GitHub Pages는 주소가 둘이 되지 않게 쓰지 않음). 앱스토어 앱 대신 설치형 웹앱(PWA)으로 — 페이지는 항상 최신을 먼저 받고, 버전 고정된 모델만 저장해 인터넷을 끊어도 카메라·인식까지 동작하는 것을 확인했다. 배포 뒤 실제 주소로 보안 헤더·설치 가능 여부· 전송 0건·오프라인 실행을 다시 검사했다.

마무리

소회

이 프로젝트는 처음으로 무언가를 따라 하지 않고 시작해서 끝까지 내 판단으로 끌고 간 작업이다. Jarvischan은 Instagram에서 본 튜토리얼에서, 인하 AI 챌린지는 팀 과제에서 출발했지만, Shadow Mitts는 "카메라로 자세를 인식해 직접 싸우는 복싱 게임"이라는 아이디어부터 내 것이었다. 참고할 튜토리얼이나 완성된 예제 없이, 무엇을 만들지·어느 방향으로 갈지·무엇이 이상한지·언제 멈출지를 처음부터 끝까지 스스로 생각해서 정했다. 코드는 Claude Code가 썼고 설계 초안과 여러 아이디어도 Claude와 함께 다듬었지만, 그 도구들에게 무엇을 시킬지와 나온 결과가 맞는지는 매번 내가 직접 몸으로 해 보고 판단했다.

코드를 직접 짜는 대신, 매 단계 웹캠 앞에서 직접 해 보고 "무엇이 이상한지"를 최대한 정확히 말로 옮기는 게 내 일이었다. "잔상이 남는다", "녹화에선 되는데 게임에선 안 된다" 같은 말은 처음엔 모호했지만, 그 증상을 재현할 데이터(녹화, 게임 기록, 프레임 추적)를 만들고 나서야 원인이 한 번에 드러났다. 짐작으로 세 번 고치는 것보다 측정 도구를 하나 만드는 게 빨랐다는 것 — 이 프로젝트에서 가장 크게 남은 것이다.

또 하나는 "여기서 멈춘다"를 정하는 일이었다. 게임 데이터로 분류 규칙을 계속 맞출 수 있었지만 교차 검증에서 더 나은 게 없다는 걸 확인하고 멈췄고, 두 모델 비교 실험도 포트폴리오를 위해 억지로 하지 않기로 했다. 개인정보 안내 문구는 구현이 실제로 그렇게 동작하는지 네트워크 기록으로 확인한 뒤에만 썼다. 다음은 슬립·더킹 같은 디펜스 동작을 넣는 M6다.
